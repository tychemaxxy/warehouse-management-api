Warehouse Management API
A RESTful API for managing shop products, product variants, pricing, and inventory using Java and Spring Boot.

Features
Create, retrieve, update, and delete products.
Manage product variants with SKU, size, color, price, and stock.
Prevent duplicate SKUs.
Process sales and prevent selling more units than available stock.
Persist application data using Spring Data JPA and H2.
Validate incoming requests and return appropriate HTTP status codes.
Run automated tests with Maven.

How to Run
Clone the repository:


git clone <YOUR_GITHUB_REPOSITORY_URL>
cd warehouse-management-api
Run the application on Windows:


.\mvnw.cmd spring-boot:run
Alternatively, build and run the executable JAR:


.\mvnw.cmd clean package
java -jar target/warehouse-management-api-0.0.1-SNAPSHOT.jar
The API will be available at:

http://localhost:8080

Database
The application uses an H2 in-memory database by default.

The database is suitable for local development and testing. Data may be lost when the application shuts down.

If the H2 console is enabled, it is available at:

http://localhost:8080/h2-console

Use the JDBC URL and credentials configured in src/main/resources/application.properties.

Design Decisions
Product and ProductVariant entities: A product can have multiple variants, such as different sizes and colors.
Separate variant inventory: Stock and SKU are tracked at the variant level so that each variant can have independent inventory.
Layered architecture: Controllers handle HTTP requests, services contain business logic, repositories access the database, and DTOs define request and response payloads.
Spring Data JPA: Simplifies persistence and entity relationships.
Transactional sales: Inventory updates are performed inside a transaction. The variant is retrieved using a repository locking query to help prevent concurrent sales from overselling stock.
Validation and exception handling: Invalid requests, missing resources, duplicate SKUs, and insufficient stock should return appropriate HTTP responses.
H2: Chosen for simplicity and ease of running the assessment without installing an external database.
Assumptions
Each product may have multiple variants.
Each variant has a unique SKU.
Price and stock are maintained per variant.
Sales requests specify a positive quantity.
A sale must not reduce stock below zero.
Product and variant IDs are generated by the database.
The default database is intended for demonstration and local testing, not production deployment.
API Endpoints
Products

Method	Endpoint	Description
POST	/api/products	Create a product
GET	/api/products	List products
GET	/api/products/{id}	Get product details
PUT	/api/products/{id}	Update a product
DELETE	/api/products/{id}	Delete a product
Product Variants

Method	Endpoint	Description
POST	/api/products/{productId}/variants	Add a variant
PUT	/api/variants/{variantId}	Update a variant
DELETE	/api/variants/{variantId}	Delete a variant
Sales

Method	Endpoint	Description
POST	/api/variants/{variantId}/sales	Sell a quantity of a variant
Confirm each endpoint against the implemented controllers before using this documentation.

Example Requests
Create a Product

POST /api/products
Content-Type: application/json

{
  "name": "Kaos Polos",
  "description": "Kaos katun"
}
Add a Variant

POST /api/products/1/variants
Content-Type: application/json

{
  "sku": "KAOS-POLOS-HITAM-M",
  "size": "M",
  "color": "Hitam",
  "price": 75000,
  "stock": 5
}
Sell Three Units

POST /api/variants/1/sales
Content-Type: application/json

{
  "quantity": 3
}
If the sale succeeds, the stock decreases from 5 to 2. A sale exceeding available stock should be rejected.
